# Rate90 比赛评分接口

项目根目录执行 `npm run dev`。BSD 实时请求从服务端环境变量 `BSD_API_TOKEN` 读取凭据。

| 用途 | GET 路径 |
| --- | --- |
| 当日已完赛比赛 | `/api/matches` |
| 指定看球日 | `/api/matches?date=2026-11-22` |
| 直接查询 BSD | `/api/matches?date=2026-11-22&source=live` |
| 读取固定样本 | `/api/matches?date=2026-11-22&source=sample` |
| 揭晓比赛与评分明细 | 在相同查询后加 `&reveal=1` |

看球日按北京时间前一天中午 12 点至当天中午 12 点划分，含起点。2026-11-22 的样本有五大联赛 10 场，2026-11-05 的样本有欧冠 2 场。

列表字段为 `id`、`stage`、`kickoff`、`home`、`away`、`rating`、`recommendation`、`topPick`。评分保留一位小数。同分按开球时间和比赛 ID 稳定排列，未评分场次排在最后。

`mode=live` 返回同步时间 `updatedAt`。部分详情读取失败时 `partial=true`。实时源不可用时，有本日样本则返回 `mode=sample`、采集日期 `capturedOn` 及 `update=upstream-unavailable`，无样本则返回 HTTP 503。成功查询的空赛日返回空列表。

## 按赛程自动采集

默认 `/api/matches` 读取已发布的比赛日。读取页面、列表或揭晓详情均使用本地数据。已有采集记录以 `mode=stored` 返回。尚未采集的日期有归档样本时返回该样本，已完整扫描的空赛日返回空列表。显式指定 `source=live` 可用于诊断供应商接口。

| 时间（北京时间） | 操作 |
| --- | --- |
| 首次运行、之后每天 12:00 | 拉取欧冠和五大联赛今日、前两天与未来七天的赛程。逐个赛事记录成功同步的日期，失败的赛事 15 分钟后重试。 |
| 开球后 125 分钟 | 首次检查完赛状态。相同赛事、相同 UTC 开球日的到期场次共用一次列表查询（按页读取）。 |
| 仍在比赛 | 15 分钟后复查。开球时间变化时按新开球时间重排，延期或取消时停止轮询原场。 |
| 确认完赛 | 读取单场详情，保存评分依据，计算评分并发布榜单。 |
| 首采后 6 小时 | 再取详情，处理供应商更正。仍缺评分依据时，首采后 24 小时补查一次。网络临时失败延后 15 分钟重试。 |

例如凌晨 03:00 开球，05:05 首查，仍在进行则 05:20 再查。若 05:20 确认完赛并取得详情，11:20 复查，必要时次日 05:20 最后补查。

在项目目录运行以下命令启动常驻采集器。

```sh
npm run collect:watch
```

常驻进程每五分钟查看本地待办，在两次扫描之间有比赛到点时提前唤醒。`npm run collect` 只运行一轮。进程重启会接续 SQLite 任务。两个进程同时启动时，数据库锁确保只有一个执行采集。数据库默认存放在 `data/collector/`，可用 `RATE90_STATE_DIR` 指定持久目录。`BSD_API_TOKEN` 从环境或项目下的 `.env.local` 读取。

旧快照有 83 个可查询的已赛 ID 缺少过程分，首次运行时自动入队，每批最多补 8 场，优先处理新完赛比赛。取得完整过程数据的历史比赛直接发布，字段不足的次日再查。保留已有参考分和最近一次完整评分。

Linux 用户服务模板在 [rate90-collector.service](../deploy/rate90-collector.service)。模板使用 `~/Rate90` 和系统 PATH 中的 Node。项目路径不同时修改 `WorkingDirectory`，通过 nvm 安装 Node 时把 `ExecStart` 中的 Node 换为实际绝对路径。以下命令安装并启动用户服务。

```sh
install -Dm644 deploy/rate90-collector.service ~/.config/systemd/user/rate90-collector.service
systemctl --user daemon-reload
systemctl --user enable --now rate90-collector.service
journalctl --user -u rate90-collector.service -f
```

静态页面和采集器应共用 `public/ui/data/`。采集器先发布按内容生成文件名的比赛日详情，再原子替换 `collected-index.js`。独立静态托管时，发布流程需要把这两部分同步到托管站点。逐脚记录、SQLite 队列和凭据仅保存在采集机器上。

## 固定算法 rate90-1.0.1

常规时间含伤停补时，划分六个 15 分钟时段。有半场标记时，补时归入对应半场的末段。加时赛和点球大战单列在常规时间评分之外。一次射门满足进球、中柱、xG ≥ 0.15 或 xGOT ≥ 0.35 任一条件，计一次关键机会。乌龙球计入比分进程和进球看点，射门、射正、关键机会及 xG 只统计进攻方实际射门。逐脚 xG、机会球队归属和分段计数须完整且一致，否则返回 `rating: null` 和“资料不足”。

下表中 `C(x,k) = min(1, max(0, x/k))`。每项系数乘以权重即得该项分，先按百分制保留一位小数，六项相加后除以 10 并四舍五入到一位。权重、上限和阈值为产品参数。同一份输入的评分与同日其他比赛无关。

| 维度 | 权重 | 计算 |
| --- | ---: | --- |
| 进攻威胁 | 25 | 有效 xG = 全场 xG − 0.5 × 明确标记为场内点球的 xG。70% 看有效 xG 总量（4 封顶），30% 看每脚有效 xG（0.18 封顶）。 |
| 进攻节奏 | 15 | 55% 看射门量（32 脚封顶），45% 看关键机会量（10 次封顶）。 |
| 看点持续性 | 20 | 60% 看六段关键机会数，每段最多计 2 次，总上限 12。40% 看 `1 − 最长连续无关键机会段数 / 6`。 |
| 双方对抗 | 15 | 均衡度 = 机会较少一方次数 × 2 / 总次数。逐脚资料齐全时，70% 看均衡度，30% 看双方同段威胁（3 段封顶）。有合格压力曲线时，上述结果占 80%，持续攻势的换边次数占 20%（5 次封顶）。整体再乘 `C(较少一方次数,3)`。 |
| 射门与扑救看点 | 10 | 进球、中柱、高难度扑救各计 1。射正后 xGOT ≥ 0.35 且比起脚 xG 高至少 0.25，该脚增加 0.25 的精彩度。累计 6 封顶。 |
| 比赛悬念 | 15 | 65% 看平局或只差一球的常规时间占比。35% 取三项中的最大值：扳平与反超次数（3 次封顶）、76 分钟起扳平或取得领先（1 次封顶）、末段威胁。末段威胁 = `C(末段关键机会,3) × 末段平局或一球差分钟数 / 15`。整项乘 `C(全场关键机会,4)`。 |

8.0 分起建议看全场，4.5–7.9 分建议看集锦，低于 4.5 分可跳过。首位达到全场门槛的比赛获得 `topPick`。

### 证据口径

- 汇总样本保留了分段射门、分段关键机会、双方机会、总 xG、有值的 xGOT 数及高难度扑救数。对抗按双方机会总数计算，精彩度按有记录的进球和高难度扑救估算，上限为关键机会数。缺少这两项依据时，精彩度按关键机会数估算（12 次封顶）。xGOT 有值次数只用于判断覆盖。
- 逐脚数据提供射正次数及 xGOT 覆盖。扑救的 xGOT ≥ 0.35 计高难度扑救。缺少 xGOT 时，xG ≥ 0.35 的被扑射门单列为机会质量代理。供应商补估和来源未知的 xG 分别记录数量。
- 逐球比分优先由进球事件重建，也可用射门结果重建。归属、排序及两队最终进球数均须可核对。在只有终场比分和分段机会时，悬念的两项分别用 `1 − C(终场净胜球,4)` 和 `C(末段机会,3)` 估算。0∶0 能确定全程持平。缺少常规时间比分时，只用末段机会强度与全场机会系数。
- 压力曲线至少覆盖 72 个常规时间分钟，每个 5 分钟段至少覆盖 3 分钟。相邻两段的平均压力方向相反，且各自绝对值达到全场平均绝对压力的一半，计一次换边。
- 球队、联赛、轮次用于匹配与筛选。赛后积分榜缺少对应比赛的赛前快照。世界杯历史页有一条可核查的进攻传球链，当前赛季样本没有逐次传递、战术指令和失误归因，以上项目均不进入该版过程分。

### 揭晓与复算

`details.analysis.components` 返回六项权重和实得分。`highlightMethod`、`suspenseMethod`、`exchangesMethod` 记录每场实际采用的依据。`details.shotEvidence` 在有逐脚资料时包含射正覆盖、射门质量提升、点球、同段对攻、压力变化及可核对的比分进程。原有比分、分段次数和 `reason` 也在揭晓后返回。`details.processRank` 按公开的一位小数评分并列排名，`details.goalsOnlyRank` 按同批次常规时间总进球数并列排名。

`node scripts/build-offline-sample.mjs` 用同一个后端函数生成离线榜单、揭晓详情与 `process-ratings.js`。当前赛季快照的 198 场中，12 场有 Rate90 过程分，83 场展示 MustWatch90 参考分，103 场待赛。原始参考分保存在 `fixtures.js`，可与过程分对照。运行 `npm test` 检查 API、静态快照和评分边界。
